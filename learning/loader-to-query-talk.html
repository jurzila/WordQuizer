From route loaders to a query cache

How lesson create, rename and delete moved from router.invalidate() to TanStack Query in two sessions, and what broke along the way.

The router caches by URL. Query caches by data. Once two screens show the same data, you want the second one.

0:0030 s

The problem: who owns server data?

We had two sources of truth. Route loaders fetched lessons, and a global WordAppContext also held words and collections.

  • A grep showed nothing read the context copies. Both hooks still fetched on every page load.
  • Fix: delete them. Context now holds only auth: token, email and the login, register and logout handlers.
  • Context earns its place when a hook has state that must be a single instance. Data fetching didn't need that.
0:3075 s

Stage 1: loader + router.invalidate()

loader: () => getCollections(),

const handleCreate = async (name: string) => {
  await createCollection(name);   // 1. the write lands
  await router.invalidate();      // 2. loaders re-run, list is fresh
};
  • The router only sees navigations, not fetches. A POST in a click handler doesn't reach its cache, so invalidate() tells it the data changed.
  • Both awaits are needed. Without the first, the refetch can beat the POST. Without the second, the form closes and the old list flashes.
  • Refetching beats setState(prev => [...prev, item]): the server may sort, trim or reject, and a local copy drifts.
  • Limit: the router cache is keyed by route match, so invalidate() re-runs every matched loader. That's all or nothing.
1:4545 s

Stage 2: key the cache by data

A query key is an array that names a piece of server data. Invalidation matches by prefix.

// src/queries.ts — one definition, shared by loader and component
export const collectionsQuery = queryOptions({
  queryKey: ["collections"],
  queryFn: getCollections,
});
  • ["collections"] matches ["collections", id] and ["collections", id, "words"] too. Pass exact: true or design flatter keys when you don't want that.
  • The Java version is Spring's @CacheEvict. router.invalidate() works like allEntries = true.
2:3060 s

Wiring: the router warms, the component subscribes

main.tsx + __root.tsx
const queryClient = new QueryClient();
const router = createRouter({
  routeTree,
  context: { queryClient },
});

createRootRouteWithContext<{
  queryClient: QueryClient
}>()({ component: … })
lessons/index.tsx
loader: ({ context }) =>
  context.queryClient.query({
    ...collectionsQuery,
    staleTime: "static",
  }),

// in the component
const collections =
  useSuspenseQuery(collectionsQuery).data;
  • The client goes in router context, not an import, so each test can inject a fresh cache. It's constructor injection, not a static field.
  • The loader still starts the fetch on navigation, so there's no waterfall. "static" returns cached data without blocking.
  • useLoaderData() is a snapshot. useSuspenseQuery is a subscription, which is what re-renders when the cache changes.
3:3045 s

Mutations

const createMutation = useMutation({
  mutationFn: (name: string) => createCollection(name),
  onSuccess: () =>
    queryClient.invalidateQueries({ queryKey: collectionsQuery.queryKey }),
});

<LessonsPage onCreate={createMutation.mutateAsync} … />
  • onSuccess returns the invalidation promise. That keeps the mutation pending until the refetch lands, which is the same job the second await did in stage 1.
  • Pass mutateAsync, not mutate. The page's own await and try/catch keep working unchanged.
  • LessonsPage didn't change, and its 4 tests passed untouched. Handlers come in as props.
4:1545 s

What bit us

The cache outlives logout

User B logs in on the same tab, and the "static" loader serves user A's lessons. Fix: queryClient.clear() in handleLogout.

data ?? []

useQuery types data as possibly undefined. Defaulting it shows "No lessons yet" to someone who has lessons. Use useSuspenseQuery instead.

ensureQueryData is deprecated

In 5.104 the replacement is query({ …, staleTime: "static" }). Most tutorials still show the old call, so check the installed .d.ts.

<Link> needs a router

Taking useRouter out of a page doesn't remove its router dependency. Tests render through a memory-history router.

If someone asks

Why keep the loader at all?
It starts the fetch when navigation begins, before the component mounts. Without it, nested routes fetch one after another, a waterfall.
Why one request on load, not two?
useSuspenseQuery raises staleTime to at least 1000 ms, so it doesn't refetch right after the loader. Come back a few seconds later and you'll see the background refetch.
Why Promise<unknown> on the page props?
The page only awaits and never reads the value. Promise<Collection> isn't assignable to Promise<void>.
What's not done yet?
The lesson detail route still uses a plain loader. There's no global 401 handling, so an expired token skips clear(). Still no route-level tests.
